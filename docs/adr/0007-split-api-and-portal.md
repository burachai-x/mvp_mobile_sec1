## บริบท

แผนเดิมให้ Laravel ตัวเดียวเสิร์ฟทั้ง `/api/v1` (แอปคนขับ) และ `/staff` (Staff Portal)
ในคอนเทนเนอร์เดียว เพื่อลดจำนวน service ที่ต้องดูแลใน MVP

หลังจากตัดสินใจใช้ **envelope encryption** และ **ถอดรหัสเอกสารฝั่ง server** (ADR 0005)
มีข้อเท็จจริงหนึ่งโผล่ขึ้นมาที่เปลี่ยนการชั่งน้ำหนัก

> **แอปของคนขับไม่เคยดาวน์โหลดเอกสารเลย** — มีแต่เจ้าหน้าที่ที่เปิดดู
> ดังนั้น `DOCUMENT_KEK` ซึ่งถอดสำเนาบัตรประชาชนได้ทุกใบ **จำเป็นเฉพาะฝั่ง Portal**

ถ้ารวมไว้คอนเทนเนอร์เดียว = service ที่เปิดสู่อินเทอร์เน็ตให้แอปคนขับ **ถือกุญแจที่ไม่เคยต้องใช้**
ช่องโหว่ใดๆ ใน `/api/v1` (RCE, path traversal, SSRF, deserialization) จะเข้าถึงกุญแจนั้นได้ทันที

## การตัดสินใจ

**แยก `api` กับ `portal` เป็นคนละ container ตั้งแต่แรก แต่ใช้โค้ดเบสและ image เดียวกัน**

### แยกอะไร

| | `api` | `portal` |
|---|---|---|
| hostname | `api.example` | `staff.example` (จำกัด IP / VPN) |
| route ที่ลงทะเบียน | `/api/v1` เท่านั้น | `/staff` เท่านั้น |
| `DOCUMENT_KEK` | **ไม่ mount** | mount |
| `NATIONAL_ID_ENCRYPTION_KEY` | **ไม่ mount** | mount |
| network `garage-net` | **ไม่อยู่** | อยู่ |
| certificate pinning จากแอป | ✅ pin | ไม่เกี่ยว (browser) |

`worker` (queue) ได้ KEK เพราะต้องทำงานเข้ารหัส/ถอดรหัสเอกสาร
`scheduler` **ไม่ต้องมี KEK** เพราะ retention ใช้ crypto-shredding คือ *ลบ* `dek_wrapped` ไม่ได้ *ถอด* อะไร (§10.3)

### ไม่แยกอะไร

**ไม่แยกโค้ดเบส** — Laravel ตัวเดียว build เป็น image เดียว รันเป็นคนละ container
เลือก role ด้วย env `APP_ROLE=api|portal` ซึ่งกำหนดว่า route ชุดไหนถูกลงทะเบียน

เหตุผล: แยกโค้ดเบสจะทำให้ model / migration / policy ซ้ำสองชุดและ drift ออกจากกันแน่นอน
ขณะที่ประโยชน์ที่ต้องการ — **API ไม่มีกุญแจและไม่มีเส้นทางถึงเอกสาร** — ได้ครบจากการแยก container อยู่แล้ว

**การปิด route ต้องทำที่ระดับ route registration ไม่ใช่ middleware** — route ของอีกฝั่งต้อง
**ไม่ถูกลงทะเบียนเลย** ในกระบวนการนั้น จะได้ `404` ตามธรรมชาติ ไม่ต้องพึ่ง middleware ที่อาจถูกข้าม

## ผลที่ตามมา

**ผลดี**
- **ลดความรุนแรงของ S14 อย่างมีนัยสำคัญ** — ช่องโหว่ใน API ที่เปิดสู่อินเทอร์เน็ต ไม่ได้กุญแจและไปไม่ถึง Garage
  ต้องเจาะ Portal ซึ่งจำกัด IP / อยู่หลัง VPN ได้ ซึ่งยากกว่ามาก
- **บังคับที่ระดับเครือข่าย ไม่ใช่แค่ config** — `api` ไม่อยู่บน `garage-net` จึงต่อไม่ได้แม้รันโค้ดอะไรก็ตาม
- แยก scale ได้: API รับโหลดจากคนขับทุกคน ส่วน Portal มีผู้ใช้ไม่กี่คน
- แยก rate limit, log, alert และ resource limit ตามลักษณะการใช้งานจริง
- Portal จำกัด IP หรือบังคับ VPN ได้โดยไม่กระทบแอปคนขับ — ทำไม่ได้ถ้ารวมกัน

**ผลเสีย / ต้นทุน**
- container เพิ่มจาก 7 เป็น 8 (dev 9) และ compose ซับซ้อนขึ้น
- ต้องดูแล 3 hostname + certificate (`api.` / `staff.` / `dl.`)
- deploy ต้องอัปเดตหลาย container พร้อมกัน — **migration ต้องเข้ากันได้ทั้งเวอร์ชันเก่าและใหม่ระหว่างช่วง rollout**
- ต้องระวังไม่ให้ `APP_ROLE` ตั้งผิด — ตั้ง `portal` ให้ container ที่เปิดสู่เน็ตคือช่องโหว่ทันที
  → **ต้องมี test ที่ยืนยันว่า image ที่รันด้วย `APP_ROLE=api` ไม่มี route `/staff` และไม่มี KEK**

## ทางเลือกที่พิจารณาแล้วไม่เลือก

| ทางเลือก | เหตุผลที่ไม่เลือก |
|---|---|
| รวมคอนเทนเนอร์เดียว (แผนเดิม) | service ที่เปิดสู่อินเทอร์เน็ตถือกุญแจที่ถอดเอกสารได้ทั้งฐานโดยไม่จำเป็น |
| แยกเป็นคนละโค้ดเบส / คนละ repo | model, migration, policy ซ้ำสองชุดและ drift แน่นอน — ต้นทุนสูงเกินประโยชน์ที่เพิ่มขึ้น |
| รวมคอนเทนเนอร์ แต่แยกแค่ php-fpm pool | pool แยก process ได้ แต่ **ยังอยู่ใน container เดียวกัน** จึงเห็น secret และ network เดียวกัน ไม่ได้แก้ปัญหาหลัก |
| แยกเฉพาะ endpoint ดาวน์โหลดเป็น service ที่สาม | ได้ isolation ของ KEK เหมือนกัน แต่ Portal ก็ต้องอ่านข้อมูล PII อื่นอยู่ดี แยกเป็น 2 ฝั่งตามผู้ใช้จริงตรงไปตรงมากว่า |
