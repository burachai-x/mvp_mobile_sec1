# ADR 0005 — Envelope encryption สำหรับเอกสารคนขับ และการเลิกใช้ presigned URL

| | |
|---|---|
| สถานะ | ยอมรับแล้ว — **แทนที่การตัดสินใจเรื่อง presigned URL ใน ADR 0004** |
| วันที่ | 2026-07-22 |
| เกี่ยวข้องกับ | ADR 0004 · `docs/architecture.md` §8, §9, §10.3 · threat model S14 |

## บริบท

เจ้าของงานเพิ่มข้อกำหนด 2 ข้อที่กระทบการออกแบบใน ADR 0004 โดยตรง

1. **สำเนาบัตรประชาชนและใบขับขี่ต้องเข้ารหัสตามมาตรฐาน**
2. **การดาวน์โหลดเอกสารต้องมีสิทธิ์ ต้องใส่ PIN และต้องเก็บประวัติทุกครั้ง**

ADR 0004 กำหนดให้ดาวน์โหลดผ่าน **presigned URL** โดยให้ browser คุยกับ Garage ตรง และ **ห้าม proxy ไฟล์ผ่าน PHP**
เหตุผลตอนนั้นคือไม่อยากให้ php-fpm worker ถูกยึดไว้ระหว่างส่งไฟล์

**ข้อกำหนดใหม่ทำให้วิธีนั้นใช้ไม่ได้อีกต่อไป**

## การตัดสินใจ

### 1. Envelope encryption ด้วย AES-256-GCM

```
ไฟล์ต้นฉบับ ──AES-256-GCM ด้วย DEK (สุ่มใหม่ทุกไฟล์)──► ciphertext ──► Garage
                   │
                   └──ห่อด้วย KEK (AES-256-GCM)──► dek_wrapped ──► PostgreSQL
```

- **DEK** สุ่ม 256-bit ใหม่ต่อไฟล์ ไม่เคยถูกเก็บเป็น plaintext ที่ใด
- **KEK** อยู่ใน Docker secret มี `kek_version` เพื่อหมุนได้โดยไม่ต้องเข้ารหัสไฟล์ใหม่ทั้งหมด
- **AES-256-GCM** เป็น AEAD ให้ทั้งความลับและการตรวจสอบความถูกต้องในตัว
  **ห้ามใช้ AES-CBC หรือโหมดที่ไม่มี authentication** — จะเปิดช่องให้แก้ ciphertext โดยตรวจไม่พบ
- IV สุ่มใหม่ทุกครั้ง **ห้ามใช้ IV ซ้ำกับ key เดิม** (GCM สูญเสียความปลอดภัยทันทีถ้า IV ซ้ำ)
- ใช้ library มาตรฐานของภาษา **ห้ามประกอบ primitive เอง**

### 2. เลิกใช้ presigned URL — ดาวน์โหลดผ่าน endpoint ของแอปแทน

**กลับคำจาก ADR 0004** เพราะ

1. presigned URL ให้ browser ได้ **ciphertext** ซึ่งผู้ใช้เปิดไม่ออก การถอดรหัสต้องเกิดฝั่ง server เพราะ KEK อยู่ที่นั่น
2. presigned URL เป็นลิงก์ที่ **ใช้ซ้ำได้จนกว่าจะหมดอายุ** จึงบังคับใส่ PIN ต่อครั้งไม่ได้
   และ **นับจำนวนครั้งที่ดาวน์โหลดจริงไม่ได้** เพราะการดาวน์โหลดไม่ผ่าน server เรา — ขัดกับข้อกำหนดเรื่องเก็บประวัติโดยตรง

flow ใหม่: ตรวจสิทธิ์ → ตรวจ elevated session (PIN) → เขียน audit → ดึง ciphertext จาก Garage → ถอดรหัสแบบ stream → ส่งต่อ

## ผลที่ตามมา

**ผลดี**
- **ciphertext-at-rest จริง** — bucket ที่ตั้งค่าผิดเป็น public หรือดิสก์ถูกขโมยไปทั้งลูก ก็ยังอ่านไม่ได้
  ลดความรุนแรงของ S14 จาก "ข้อมูลรั่วทั้งฐาน" เหลือ "ciphertext รั่ว"
- **backup ของ Garage เป็น ciphertext อยู่แล้ว** ความเสี่ยงของ backup ลดลงมาก
- ได้ **crypto-shredding ฟรี** — ลบ `dek_wrapped` = ไฟล์กู้ไม่ได้ตลอดกาล
  ทำให้ requirement เรื่อง retention (§10.3) ทำได้สะอาด โดยไม่ต้องลบแถวและไม่ทำลาย audit trail
- บังคับ PIN และเก็บประวัติต่อการดาวน์โหลดแต่ละครั้งได้จริง

**ผลเสีย / ต้นทุน**
- **php-fpm worker ถูกยึดระหว่างส่งไฟล์** — สิ่งที่ ADR 0004 พยายามเลี่ยง
  ยอมรับได้เพราะเป็น path ที่มีปริมาณต่ำมาก (เจ้าหน้าที่เปิดดูเอกสารวันละไม่กี่ครั้ง) มาตรการลด: จำกัดไฟล์ 10 MB, stream ทีละ chunk ห้ามโหลดทั้งไฟล์เข้า memory, แยก php-fpm pool สำหรับ route ดาวน์โหลด
- **KEK กลายเป็นจุดตายเดียวของระบบ** — หายเมื่อไหร่เอกสารทุกไฟล์กู้ไม่ได้
  ต้องมีสำเนาสำรองออฟไลน์แยกสถานที่ และ **ห้ามเก็บไว้ที่เดียวกับ backup ของ PostgreSQL** (ที่มี `dek_wrapped` อยู่)
  ถ้าทั้งสองอย่างอยู่ที่เดียวกัน envelope encryption ไม่ได้ป้องกันอะไรเลย
- ค้นหาในเนื้อเอกสารไม่ได้ (ยอมรับได้ — ไม่มี requirement นี้)
- ต้องซ้อมกู้คืนแบบครบวงจร (DB + Garage + KEK → เปิดไฟล์ได้) อย่างน้อยปีละครั้ง

## ทางเลือกที่พิจารณาแล้วไม่เลือก

| ทางเลือก | เหตุผลที่ไม่เลือก |
|---|---|
| **SSE-S3** (Garage ถือกุญแจเอง) | กุญแจอยู่ที่เดียวกับข้อมูล — ใครเข้าถึง Garage ได้ก็อ่านได้หมด ไม่ได้ป้องกันภัยคุกคามที่เราสนใจ |
| **SSE-C** (ส่งกุญแจมากับ request) | ใช้กับ presigned URL ที่ browser เรียกตรงไม่ได้ เพราะต้องส่ง header กุญแจไปด้วย |
| **เข้ารหัสทั้ง bucket ด้วยกุญแจเดียว** | ไม่มี crypto-shredding รายไฟล์ → ลบข้อมูลรายบุคคลตาม retention ไม่ได้ และหมุนกุญแจต้องเข้ารหัสใหม่ทั้งหมด |
| **เข้ารหัสฝั่ง client (browser)** ก่อนอัปโหลด | กุญแจต้องไปอยู่ที่ browser ของเจ้าหน้าที่ จัดการ lifecycle ยากและเสี่ยงกว่า ไม่ได้ประโยชน์เพิ่มเพราะ server ต้องอ่านไฟล์ได้อยู่แล้ว |
| **เก็บ presigned URL ไว้แล้วเข้ารหัสด้วย SSE** | แก้ปัญหาเรื่องอ่านไฟล์ได้ แต่ยังบังคับ PIN ต่อครั้งและนับการดาวน์โหลดไม่ได้ ซึ่งเป็นข้อกำหนดตรงๆ |
