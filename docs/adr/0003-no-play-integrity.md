# ADR 0003 — ไม่ทำ Play Integrity / App Attest (ตัดถาวร)

| | |
|---|---|
| สถานะ | ยอมรับแล้ว — **เจ้าของงานตัดสินใจ 2026-07-22** (แทนที่ฉบับก่อนที่ระบุว่า "เลื่อนเป็น Phase 2") |
| วันที่ | 2026-07-22 |
| เกี่ยวข้องกับ | `PRD.md` §2.2 · `docs/architecture.md` §4, §11 · threat model S5 · ADR 0006 |

## บริบท

`PRD.md` §2.2 ให้ตรวจ root/jailbreak/emulator ฝั่ง client แล้วปิดแอปเมื่อพบ
ผลตรวจฝั่ง client เชื่อไม่ได้ — Magisk Hide, Zygisk, Frida ซ่อน root จากทุกวิธีตรวจที่รันบนเครื่องเดียวกันได้

การตรวจที่เชื่อได้จริงต้องมาจากภายนอกเครื่อง คือ **Play Integrity API** (Android) หรือ **App Attest** (iOS)

**เจ้าของงานตัดสินใจไม่นำแอปขึ้น store ใดๆ และไม่ทำ store ของตัวเอง** เหตุผลคือไม่ต้องการให้คนภายนอกรู้ว่ามีแอปนี้อยู่
แอปจะแจกเป็นไฟล์ APK โดยตรงและอัปเดตตัวเองผ่านเว็บของระบบ (ADR 0006)

**Play Integrity API ต้องมี Play Console จึงจะเรียกใช้ได้** — เมื่อไม่ขึ้น Play Store จึงใช้ไม่ได้ **ทางเทคนิค**
ไม่ใช่เรื่องงบประมาณหรือลำดับความสำคัญ

## การตัดสินใจ

**ไม่ทำ L3 และไม่วางแผนจะทำ**

1. ยังทำตาม `PRD.md` §2.2 — แอปตรวจ root/emulator/developer options/mock location แล้วปิดแอปเมื่อพบ
2. ยังบังคับส่งผลตรวจขึ้น server ทุกครั้งที่เปิดแอป (`POST /devices/me/integrity`) เก็บใน `integrity_reports`
   → server เป็นคนตัดสิน `allow`/`warn`/`block` ไม่ปล่อยให้ client ตัดสินฝ่ายเดียว
   → ถึงสัญญาณจะปลอมได้ แต่อย่างน้อยเรา **เห็นแนวโน้ม** และรู้ว่ามีเครื่องผิดปกติเข้ามาแค่ไหน
3. คง `IntegrityVerifier` interface + `NullVerifier` ไว้ เผื่อนโยบายเปลี่ยนในอนาคต
   **แต่ห้ามสื่อสารกับลูกค้าว่า "จะทำใน Phase 2"** — ภายใต้ข้อจำกัดปัจจุบันไม่มี Phase 2
4. ชดเชยด้วยมาตรการฝั่ง server (§11.4) โดยเข้าใจว่าเป็นการ **ตรวจจับ** ไม่ใช่ **ป้องกัน**

## ผลที่ตามมา

**ผลดี**
- ไม่ต้องพึ่งบัญชี Google/Apple และไม่ต้องเปิดเผยการมีอยู่ของแอปต่อสาธารณะ ตรงตามความต้องการทางธุรกิจ
- ลดความซับซ้อนและ dependency ภายนอกลงจริง

**ผลเสีย — ต้องบอกลูกค้าให้ชัดเป็นลายลักษณ์อักษร**
- **ความเสี่ยง S5 ลดลงได้ด้วย Key Attestation แต่ยังปิดไม่หมด**
  Key Attestation จับเครื่องที่ปลดล็อก bootloader ได้ (ซึ่งเป็นเคสส่วนใหญ่ของเครื่อง root)
  แต่เครื่องที่ bootloader ล็อกอยู่แล้วถูก exploit ระดับ runtime ยังหลุดได้ และตรงนี้ **ปิดไม่ได้ถาวร**
- **ข้อกำหนด `PRD.md` §2.2 จะไม่บรรลุเจตนาอย่างถาวร** — สิ่งที่ส่งมอบได้คือ "ตรวจแล้วรายงาน" ไม่ใช่ "ป้องกันได้"
  ถือเป็นการเปลี่ยนขอบเขตของ requirement ไม่ใช่การเลื่อน
- ไม่มี Play Protect สแกนมัลแวร์ ไม่มีการอัปเดตอัตโนมัติ ไม่มีการเพิกถอนจากส่วนกลาง (ADR 0006)
- ต้องสร้างกลไกอัปเดตเอง ซึ่งกลายเป็นช่องโจมตีใหม่ที่รุนแรงกว่าสิ่งที่ L3 ปิด (ADR 0006, threat model S16)

## ✅ สิ่งที่ใช้ทดแทนได้บางส่วน — Android Key Attestation

**Play Integrity ไม่ใช่ทางเดียวที่ตรวจสภาพเครื่องฝั่ง server ได้**

Android Key Attestation ให้ TEE/StrongBox ของเครื่องเซ็น certificate chain ที่สืบสาวถึง root ของ Google
ในนั้นมี `verifiedBootState`, `deviceLocked`, `securityLevel`, `osPatchLevel`
และ **ไม่ต้องมี Play Console หรือ Play Services** — เป็นความสามารถของ Android framework เอง

→ **ใช้ใน MVP** เป็นชั้น L2.5 ปฏิเสธการ enroll เมื่อ `verifiedBootState != Verified` หรือ bootloader ปลดล็อก
เครื่อง root ส่วนใหญ่ต้องปลดล็อก bootloader ก่อน จึงถูกจับได้ตรงนี้ และแอปปลอมค่าไม่ได้เพราะไม่มีกุญแจของ TEE

**สิ่งที่ยังต่างจาก Play Integrity:** ตรวจได้แค่สถานะตอน boot ไม่ได้ตรวจว่าตอนนี้มี Frida รันอยู่ไหม
เครื่องที่ bootloader ล็อกแต่ถูก exploit ภายหลังยังหลุดได้ — ส่วนนี้ยังปิดไม่ได้

รายละเอียดและข้อจำกัดครบใน `docs/architecture.md` §4.2

## หมายเหตุ — iOS

App Attest ของ Apple **ไม่ได้บังคับว่าแอปต้องอยู่บน App Store** เสมอไป (รองรับการแจกแบบองค์กรได้ในบางเงื่อนไข)
ต่างจาก Play Integrity ที่ผูกกับ Play Console แน่นอน

**MVP นี้ทำ Android เท่านั้น** จึงยังไม่ต้องตัดสินใจเรื่องนี้
บันทึกไว้เผื่ออนาคต: ถ้าขยายไป iOS ควรตรวจสอบเงื่อนไขของ Apple Developer Enterprise Program ก่อน อย่าเพิ่งสรุปว่าทำไม่ได้

## ทางเลือกที่พิจารณาแล้วไม่เลือก

| ทางเลือก | เหตุผลที่ไม่เลือก |
|---|---|
| ขึ้น Play Store แบบ internal testing track (ไม่เปิดสาธารณะ) | จะได้ Play Integrity โดยแอปไม่ปรากฏต่อสาธารณะ — **แต่เจ้าของงานปฏิเสธการขึ้น store ทุกรูปแบบ** เก็บไว้เป็นทางเลือกถ้านโยบายเปลี่ยน |
| เขียน root detection เองแบบลึก (ตรวจ `/proc`, seccomp, ตรวจ Frida ในหน่วยความจำ) | เป็นเกมวิ่งไล่ที่แพ้ในระยะยาว ลงแรงมากแล้วยัง bypass ได้ และเมื่อไม่มี L3 มารองรับก็ยิ่งไม่คุ้ม |
| ทำ attestation เองด้วย server challenge | ทุกอย่างที่รันบนเครื่องผู้ใช้ปลอมได้ — attestation ที่ไม่มี root of trust ในฮาร์ดแวร์จากผู้ผลิต ไม่ได้พิสูจน์อะไร |
