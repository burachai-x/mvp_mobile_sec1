# ADR 0008 — ไม่มี CI pipeline · คุณภาพและการ build ขึ้นกับคนและ `make`

| วันที่ | 2026-09-21 |
| เกี่ยวข้องกับ | **แทนที่ส่วนที่ว่าด้วย CI ของ ADR 0002** · `CLAUDE.md` §3, §4, §5 · `docs/security/threat-model.md` S8 · `PRD.md` §2.1 |

## บริบท

เอกสารชุดแรกของโปรเจกต์เขียนขึ้นโดยสมมติว่าจะมี CI pipeline และผูกกฎสำคัญหลายข้อไว้กับมัน

- `CLAUDE.md` §3 — PR ต้องผ่าน CI ครบ (lint + static analysis + test + secret scan) ก่อน merge
- `CLAUDE.md` §4 — tag ได้เฉพาะคอมมิตที่ CI ผ่าน
- ADR 0002 — Flutter release build ทำใน CI โดย decode `.jks` จาก secret ลง tmpfs แล้วลบทิ้ง
- threat model S8 — มาตรการกัน `.jks` หลุดคือ "อยู่ใน CI secret เท่านั้น"

**แต่ repo ไม่เคยมี CI จริง** ไม่มี `.github/workflows/` และไม่มีที่อื่นที่รันคำสั่งเหล่านี้ให้
กฎที่อ้าง CI จึงไม่เคยถูกบังคับเลยสักข้อ — เป็นกฎที่อ่านแล้วดูรัดกุมแต่ในทางปฏิบัติว่างเปล่า

ซึ่งอันตรายกว่าการไม่มีกฎ เพราะคนอ่านเข้าใจว่ามีตาข่ายรองรับอยู่

## การตัดสินใจ

**ยอมรับว่าไม่มี CI และเขียนกฎใหม่ให้ตรงกับสิ่งที่บังคับได้จริง**

| เดิม (อ้าง CI) | ใหม่ |
|---|---|
| PR ต้องผ่าน CI ครบก่อน merge | คนเปิด PR รัน `make lint` · `make analyse` · `make test` · `make secrets-scan` เอง แล้วเขียนใน PR description ว่ารันแล้ว |
| tag ได้เฉพาะคอมมิตที่ CI ผ่าน | tag ได้เฉพาะคอมมิตที่รัน `make test` + `make analyse` ผ่าน |
| ลงนาม manifest ออฟไลน์หรือใน CI | ลงนามออฟไลน์ด้วย `scripts/sign-manifest.sh` เท่านั้น |
| gitleaks ใน pre-commit hook และ CI | gitleaks ใน `.githooks/pre-commit` + `make secrets-scan` ก่อนเปิด PR |
| Flutter release build ใน CI | build นอก Docker บนเครื่องที่ถือ `.jks` |

**สิ่งที่ไม่เปลี่ยน:** ข้อห้ามที่เป็นแก่นยังอยู่ครบ — `.jks` ห้ามเข้า repo และห้ามเข้า image layer,
`MANIFEST_SIGNING_KEY` ห้ามอยู่บนเซิร์ฟเวอร์, ห้ามปิด test หรือลด threshold ของ static analysis
เพื่อให้คำสั่งตรวจผ่าน

## ผลที่ตามมา

**ผลดี**
- เอกสารกับความจริงตรงกัน คนอ่านรู้ว่า **ไม่มีอะไรตรวจให้อัตโนมัติ** และต้องตรวจเอง
- ไม่ต้องดูแล pipeline และไม่ต้องฝาก secret ไว้กับบัญชีของบริการภายนอก

**ผลเสีย — ต้องรับไว้อย่างรู้ตัว**
- **ไม่มีอะไรกันคนลืม** ถ้าใครไม่รัน `make test` ก่อนเปิด PR ก็ไม่มีใครรู้จนกว่าจะเจอปัญหาทีหลัง
  ตาข่ายที่เหลือคือ reviewer กับ pre-commit hook เท่านั้น
- **`make verify-isolation` ไม่มีใครรันให้** ทั้งที่ ADR 0007 ระบุว่าต้องมี test ยืนยันว่า
  `APP_ROLE=api` ไม่มี KEK และ `/staff` ตอบ 404 — test เขียนไว้แล้วแต่ต้องมีคนสั่งรัน
- **build ไม่ reproducible** — เดิม ADR 0002 กำหนดให้ถือว่า "build จาก CI เท่านั้นที่เป็นของจริง"
  ตอนนี้ไม่มีจุดอ้างอิงนั้น APK ที่ปล่อยจึงเป็นผลจากเครื่องของใครคนหนึ่ง
  ทางชดเชยที่ทำได้ทันทีคือบันทึก `apk_sha256` ของทุก release ไว้ และ pin เวอร์ชัน Flutter SDK ให้ตรงกันทุกเครื่อง

## 🔴 คำถามที่ยังเปิดอยู่ — `.jks` เก็บที่ไหน

`PRD.md` §2.1 กำหนดว่า `.jks` ต้องอยู่ใน **Secure Environment (เช่น CI/CD Secrets / Vault)**
ข้อกำหนดนี้เป็นของลูกค้าและ **ไม่ได้หายไปพร้อมกับ CI** — เพียงแต่ทางเลือกหนึ่งในสองทางถูกตัดออก

**ระหว่างที่ยังไม่ตัดสิน ห้ามถือว่า "วางไว้บนเครื่อง dev" เป็นคำตอบ** เพราะขัด PRD §2.1 โดยตรง
และทำให้ S8 (`.jks` หลุด = ความเสียหายสูงสุด กู้คืนไม่ได้) กลับมาเปิดกว้าง

ทางเลือกที่เหลือ เรียงตามภาระที่ต้องลงแรง

1. **Vault / secret manager** — ตรงกับ PRD มากที่สุด แต่ต้องมีของให้ดูแลเพิ่ม
2. **เครื่องเดียวที่กำหนดไว้ชัด สำหรับ release build เท่านั้น** — เข้ารหัสดิสก์, จำกัดคนเข้าถึง,
   `.jks` ไม่ออกจากเครื่องนั้น และบันทึกไว้ว่าใครถืออยู่
3. **ฮาร์ดแวร์ token / HSM** — ปลอดภัยที่สุด ราคาและความยุ่งยากสูงสุด

ข้อ 2 เป็นทางที่ถูกที่สุดที่ยัง**อาจ**นับเป็น Secure Environment ได้ แต่ต้องให้เจ้าของงานยืนยัน
ว่ารับเงื่อนไขนี้แทนที่ CI secret ที่ PRD ยกตัวอย่างไว้

**ต้องได้ข้อสรุปก่อนปล่อย release แรกที่ลงนามด้วย production key** — ไม่ใช่ก่อนขึ้น production
เพราะ APK ที่เซ็นแล้วออกไปเครื่องคนขับ เปลี่ยน key ทีหลังคือต้องติดตั้งใหม่ทั้งฐาน
