# ADR 0008 — ไม่มี CI pipeline · คุณภาพและการ build ขึ้นกับคนและ `make`

| | |
|---|---|
| สถานะ | ยอมรับแล้ว — เจ้าของงานตัดสินใจ 2026-09-21 |
| วันที่ | 2026-09-21 |
| เกี่ยวข้องกับ | **แทนที่ส่วนที่ว่าด้วย CI ของ ADR 0002** · `CLAUDE.md` §3, §4, §5 · `docs/security/threat-model.md` S8 · `PRD.md` §2.1 |

## บริบท

เอกสารชุดแรกของโปรเจกต์เขียนขึ้นโดยสมมติว่าจะมี CI pipeline และผูกกฎสำคัญหลายข้อไว้กับมัน

- `CLAUDE.md` §3 — PR ต้องผ่าน CI ครบ (lint + static analysis + test + secret scan) ก่อน merge
- `CLAUDE.md` §4 — tag ได้เฉพาะคอมมิตที่ CI ผ่าน
- ADR 0002 — Flutter release build ทำใน CI โดย decode `.jks` จาก secret ลง tmpfs แล้วลบทิ้ง
- threat model S8 — มาตรการกัน `.jks` หลุดคือ "อยู่ใน CI secret เท่านั้น"

**แต่ repo ไม่เคยมี CI จริง** ไม่มี `.github/workflows/` และไม่มีที่อื่นที่รันคำสั่งเหล่านี้ให้
กฎที่อ้าง CI จึงไม่เคยถูกบังคับเลยสักข้อ — เป็นกฎที่อ่านแล้วดูรัดกุมแต่ในทางปฏิบัติว่างเปล่า

ซึ่งอันตรายกว่าการไม่มีกฎ เพราะคนอ่านเข้าใจว่ามีตาข่ายรองรับอยู่

## การตัดสินใจ

**ยอมรับว่าไม่มี CI และเขียนกฎใหม่ให้ตรงกับสิ่งที่บังคับได้จริง**

| เดิม (อ้าง CI) | ใหม่ |
|---|---|
| PR ต้องผ่าน CI ครบก่อน merge | คนเปิด PR รัน `make lint` · `make analyse` · `make test` · `make secrets-scan` เอง แล้วเขียนใน PR description ว่ารันแล้ว |
| tag ได้เฉพาะคอมมิตที่ CI ผ่าน | tag ได้เฉพาะคอมมิตที่รัน `make test` + `make analyse` ผ่าน |
| ลงนาม manifest ออฟไลน์หรือใน CI | ลงนามออฟไลน์ด้วย `scripts/sign-manifest.sh` เท่านั้น |
| gitleaks ใน pre-commit hook และ CI | gitleaks ใน `.githooks/pre-commit` + `make secrets-scan` ก่อนเปิด PR |
| Flutter release build ใน CI | build นอก Docker บนเครื่องที่ถือ `.jks` |

**สิ่งที่ไม่เปลี่ยน:** ข้อห้ามที่เป็นแก่นยังอยู่ครบ — `.jks` ห้ามเข้า repo และห้ามเข้า image layer,
`MANIFEST_SIGNING_KEY` ห้ามอยู่บนเซิร์ฟเวอร์, ห้ามปิด test หรือลด threshold ของ static analysis
เพื่อให้คำสั่งตรวจผ่าน

## ผลที่ตามมา

**ผลดี**
- เอกสารกับความจริงตรงกัน คนอ่านรู้ว่า **ไม่มีอะไรตรวจให้อัตโนมัติ** และต้องตรวจเอง
- ไม่ต้องดูแล pipeline และไม่ต้องฝาก secret ไว้กับบัญชีของบริการภายนอก

**ผลเสีย — ต้องรับไว้อย่างรู้ตัว**
- **ไม่มีอะไรกันคนลืม** ถ้าใครไม่รัน `make test` ก่อนเปิด PR ก็ไม่มีใครรู้จนกว่าจะเจอปัญหาทีหลัง
  ตาข่ายที่เหลือคือ reviewer กับ pre-commit hook เท่านั้น
- **`make verify-isolation` ไม่มีใครรันให้** ทั้งที่ ADR 0007 ระบุว่าต้องมี test ยืนยันว่า
  `APP_ROLE=api` ไม่มี KEK และ `/staff` ตอบ 404 — test เขียนไว้แล้วแต่ต้องมีคนสั่งรัน
- **build ไม่ reproducible** — เดิม ADR 0002 กำหนดให้ถือว่า "build จาก CI เท่านั้นที่เป็นของจริง"
  ตอนนี้ไม่มีจุดอ้างอิงนั้น APK ที่ปล่อยจึงเป็นผลจากเครื่องของใครคนหนึ่ง
  ทางชดเชยที่ทำได้ทันทีคือบันทึก `apk_sha256` ของทุก release ไว้ และ pin เวอร์ชัน Flutter SDK ให้ตรงกันทุกเครื่อง

## `.jks` เก็บที่ไหน — เครื่อง release เฉพาะ

*ตัดสินแล้ว 2026-09-21 — เจ้าของงานเลือกแนวทางนี้แทน Vault และ HSM*

`PRD.md` §2.1 กำหนดว่า `.jks` ต้องอยู่ใน **Secure Environment (เช่น CI/CD Secrets / Vault)**
เมื่อไม่มี CI แล้ว สิ่งที่ใช้แทนคือ **เครื่องเดียวที่กำหนดไว้ชัดเจน ใช้สำหรับ release build เท่านั้น**

**เครื่องนั้นนับเป็น Secure Environment ได้ก็ต่อเมื่อครบทุกข้อ** — ขาดข้อใดข้อหนึ่งมันก็เป็นแค่
เครื่อง dev ที่บังเอิญมี keystore อยู่ ซึ่งขัด PRD §2.1

1. **ดิสก์เข้ารหัสทั้งลูก** (LUKS / BitLocker / FileVault) และล็อกหน้าจอเมื่อไม่ได้ใช้
2. **`.jks` ไม่ออกจากเครื่องนั้น** — ห้ามส่งผ่านแชต อีเมล ไดรฟ์ที่แชร์ หรือ USB ที่ไม่ได้เข้ารหัส
3. **password ของ keystore ไม่อยู่บนเครื่องเดียวกับไฟล์** — เก็บใน password manager
   และ **ห้ามอยู่ใน `build.gradle`, `key.properties` ที่ commit, หรือ shell history**
4. **ระบุตัวผู้ถือเป็นชื่อคน** ไม่ใช่ "ทีม" — เขียนไว้ใน runbook ว่าใครถือ และทบทวนทุกครั้งที่มีคนเข้าออก
5. **ไม่ใช้เครื่องนั้นท่องเว็บทั่วไปหรือลงซอฟต์แวร์นอกเหนือจากที่ build ต้องใช้**
6. **มี backup ของ keystore ที่เข้ารหัส เก็บคนละที่กับเครื่อง** (ดูหัวข้อถัดไป — ข้อนี้บังคับ)

### 🔴 backup ของ keystore ไม่ใช่ของเสริม

เครื่องเดียวแปลว่า **ถ้าเครื่องพัง ถูกขโมย หรือดิสก์เสีย = เซ็น APK ตัวใหม่ไม่ได้อีกเลย**
Android ไม่ยอมให้ติดตั้งทับแอปที่เซ็นด้วย key คนละดอก ผลคือ**ต้องให้คนขับทุกคนถอนแอปแล้วติดตั้งใหม่**
ซึ่งเป็นงานภาคสนามที่แพงกว่าเหตุการณ์กุญแจหลุดในหลายกรณี

การสูญเสีย keystore จึงเป็นความเสียหายคนละแบบกับการที่มันหลุด แต่หนักพอกัน และป้องกันได้ง่ายกว่ามาก

- backup ต้อง **เข้ารหัสด้วย passphrase ที่ไม่ได้เก็บไว้ที่เดียวกับไฟล์**
- เก็บ **อย่างน้อย 2 ที่ที่ไม่พังพร้อมกัน** และอย่างน้อยหนึ่งที่อยู่นอกออฟฟิศ
- **ทดสอบกู้คืนจริงอย่างน้อยหนึ่งครั้ง** ก่อนปล่อย release แรก — backup ที่ไม่เคยลองกู้ไม่นับว่ามี

### 🔴 อย่าให้เครื่องเดียวถือกุญแจครบชุด

ถ้าเครื่อง release ถือทั้ง `.jks` **และ** `MANIFEST_SIGNING_KEY` คนที่ยึดเครื่องนั้นได้จะ
**เซ็น APK ปลอมและเซ็น manifest ที่สั่งให้ทุกเครื่องติดตั้งมันได้ในคราวเดียว** ซึ่งคือสถานการณ์
เลวร้ายที่สุดที่ `docs/security/threat-model.md` S8 กับ T8 บรรยายไว้ รวมร่างกัน

เอกสารนี้จึงกำหนดว่า **ถ้าทำได้ ให้ `MANIFEST_SIGNING_KEY` อยู่คนละที่กับ `.jks`**
ถ้าข้อจำกัดของทีมทำให้ต้องอยู่เครื่องเดียวกันจริง ให้บันทึกไว้ว่ารับความเสี่ยงข้อนี้ไว้แล้ว
และชดเชยด้วยการจำกัดคนเข้าถึงเครื่องให้แคบที่สุด

### สิ่งที่ยังต้องทำ

- [ ] เขียน `docs/runbook/release-build.md` — ขั้นตอน build release, ที่เก็บ backup, และวิธีกู้คืน
- [ ] ทดสอบกู้ keystore จาก backup หนึ่งครั้ง **ก่อน** release แรกที่เซ็นด้วย production key
- [ ] ระบุชื่อผู้ถือเครื่องลงใน runbook

**เส้นตาย: ก่อนปล่อย release แรกที่เซ็นด้วย production key** — ไม่ใช่ก่อนขึ้น production
เพราะ APK ที่เซ็นแล้วออกไปถึงเครื่องคนขับ การเปลี่ยน key ทีหลังคือติดตั้งใหม่ทั้งฐาน
