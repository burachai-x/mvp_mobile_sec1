# ADR 0001 — ใช้ device keypair ใน hardware keystore เป็นตัวผูกอุปกรณ์

| | |
|---|---|
| สถานะ | ยอมรับแล้ว |
| วันที่ | 2026-07-22 |
| เกี่ยวข้องกับ | `PRD.md` §2.3, §3 · `docs/security/threat-model.md` S1, S3 |

## บริบท

`PRD.md` กำหนดวิธีผูกอุปกรณ์ไว้ 2 ทาง

1. **§2.3** — แอปแนบ `X-App-Signature` (SHA-256 fingerprint ของ release keystore) แล้ว server เทียบกับค่าที่ลงทะเบียนไว้ ไม่ตรงตอบ `403`
2. **§3** — แอปดึง "Hardware UUID" ส่งไป enroll

ทั้งสองวิธีมีปัญหาเชิงหลักการ

**เรื่อง signature fingerprint:** ค่านี้เป็น**ค่าสาธารณะ** ใครก็ดึงจาก APK ที่เผยแพร่แล้วได้ด้วย
```
apksigner verify --print-certs app-release.apk
```
การส่งเป็น static header จึงเท่ากับส่งค่าคงที่ที่คัดลอกได้ในไม่กี่วินาที ไม่ได้พิสูจน์ว่า request มาจากแอปตัวจริง

**เรื่อง Hardware UUID:** ตัวระบุอุปกรณ์ที่เสถียรไม่มีอยู่จริงบนมือถือปัจจุบัน
- Android ตัดการเข้าถึง IMEI/serial ตั้งแต่ API 29 (Android 10); `ANDROID_ID` reset เมื่อ factory reset และผูกกับ signing key + user profile
- บนเครื่อง root ค่านี้ปลอมได้ตรงๆ

→ ถ้าผูกอุปกรณ์ด้วยสองอย่างนี้ ระบบจะกันได้แค่คนที่ไม่ตั้งใจโจมตี

## การตัดสินใจ

ใช้ **asymmetric keypair (EC P-256) ที่สร้างในฮาร์ดแวร์ของเครื่อง** เป็นตัวผูกอุปกรณ์ที่แท้จริง

- **MVP ทำ Android เท่านั้น** — Android Keystore ใช้ StrongBox เมื่อเครื่องรองรับ
- ตั้ง `export = false` — **private key ออกจากเครื่องไม่ได้ แม้ root แล้ว**
- ขอ **attestation chain** มาพร้อมกันตอนสร้าง key เพื่อให้ server ตรวจสภาพเครื่องได้ (§4.2)
- ตอน enroll แอปส่ง **public key** ขึ้น server → เก็บใน `devices.public_key`
- ทุก request หลังจากนั้นแนบ `X-Device-Signature` = ECDSA-P256 ของ
  `METHOD | PATH | sha256(body) | X-Timestamp | X-Nonce`
- server ตรวจด้วย public key ที่เก็บไว้ + ตรวจ nonce ซ้ำใน Valkey (TTL 5 นาที) + clock skew ±60 วินาที

**ไม่ตัดข้อกำหนดเดิมของ PRD ทิ้ง:**
- `X-App-Signature` ยังทำอยู่ครบตาม §2.3 แต่จัดชั้นเป็น **L1 — signal เท่านั้น ไม่ใช่ authentication**
- `device_uuid` ยังเก็บอยู่ แต่เป็น **secondary signal** ไว้ดูการโคลน/ย้ายเครื่อง และเก็บเป็น HMAC เท่านั้นตาม PDPA

## ผลที่ตามมา

**ผลดี**
- ปิด S1 (เขียน client เองยิง API ตรง) และ S3 (โคลนอุปกรณ์) ได้จริง
- เพิกถอนอุปกรณ์ทีละเครื่องได้ — ลบ/แบน public key ก็จบ
- ผูก key เข้ากับ biometric/screen-lock ของเครื่องได้ในอนาคตโดยไม่ต้องแก้ protocol

**ผลเสีย / ต้นทุน**
- แอปต้องจัดการ key lifecycle เอง (สร้าง, กู้เมื่อ keystore ถูกล้าง, จัดการตอนผู้ใช้เปลี่ยนวิธีล็อกหน้าจอ)
- **การล้าง keystore ทำให้คนขับต้อง enroll ใหม่** — เกิดขึ้นได้จริงเมื่อผู้ใช้เปลี่ยน/ถอด screen lock บน Android
  → ใช้ flow เดียวกับเครื่องหาย: เจ้าหน้าที่ revoke เครื่องเดิม + ออก activation code ใหม่ผูกกับคนขับคนเดิม
  **ไม่ต้องกรอกข้อมูลคนขับใหม่** (ดู `docs/architecture.md` §6.6)
- ทุก request มีต้นทุนคำนวณลายเซ็นเพิ่ม (เล็กน้อยสำหรับ P-256)
- อุปกรณ์เก่าบางรุ่นไม่มี StrongBox → ลดระดับเป็น TEE ซึ่งยังยอมรับได้

**สิ่งที่ยังไม่ปิด**
- L2 พิสูจน์ว่า *เครื่องนี้* เป็นเครื่องที่ลงทะเบียนไว้ **แต่ไม่ได้พิสูจน์ว่า *แอปที่เรียก* เป็นแอปตัวจริง**
- attacker ที่ root เครื่องตัวเองแล้วใช้ Frida เรียกผ่าน keystore ยังทำได้อยู่ → ต้องอาศัย L3 (ดู ADR 0003)

## ทางเลือกที่พิจารณาแล้วไม่เลือก

| ทางเลือก | เหตุผลที่ไม่เลือก |
|---|---|
| ทำตาม PRD ตรงๆ (fingerprint + UUID) | ค่าสาธารณะทั้งคู่ ปลอมได้ ไม่ได้ป้องกันอะไรจริง |
| HMAC ด้วย shared secret ฝังในแอป | secret ต้องอยู่ในแอป → ดึงออกได้ด้วย `strings` หรือ Frida ภายในไม่กี่นาที |
| Certificate pinning อย่างเดียว | กัน MITM ได้ แต่**ไม่ได้ผูกอุปกรณ์** — เป็นคนละหน้าที่กัน ใช้ประกอบกันได้ (ทำ pinning กับ API ด้วย §11.5) แต่แทนกันไม่ได้ |
| ผูกด้วย FCM/APNs token | เปลี่ยนเองได้ ไม่ได้ออกแบบมาเพื่อความปลอดภัย |
