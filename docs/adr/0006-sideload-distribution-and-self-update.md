# ADR 0006 — แจกแอปแบบ sideload และอัปเดตตัวเองผ่าน signed manifest

| | |
|---|---|
| สถานะ | ยอมรับแล้ว — เจ้าของงานกำหนด |
| วันที่ | 2026-07-22 |
| เกี่ยวข้องกับ | `docs/architecture.md` §11 · ADR 0003 · threat model S16 |

## บริบท

เจ้าของงานกำหนดว่า **ไม่นำแอปขึ้น store ใดๆ และไม่ทำ store ของตัวเอง**
เหตุผลคือไม่ต้องการให้คนภายนอกรู้ว่ามีแอปนี้อยู่

แอปจะแจกเป็นไฟล์ APK โดยตรง และ **อัปเดตตัวเองโดยเช็คจากเว็บของระบบทุกครั้งที่เปิดแอป**
ตัวอย่างที่เจ้าของงานให้มา: `https://xxx.xxx.xx/app-x/version.xd`

## การตัดสินใจ

### 1. แจกแบบ sideload — ยอมรับผลที่ตามมา

- ผู้ใช้ต้องเปิด "ติดตั้งแอปจากแหล่งที่ไม่รู้จัก" และเห็นหน้าจอยืนยันติดตั้งของระบบทุกครั้ง
- ไม่มี Play Protect, ไม่มีการอัปเดตอัตโนมัติ, ไม่มีการเพิกถอนจากส่วนกลาง
- **Play Integrity ใช้ไม่ได้** → L3 ถูกตัดถาวร (ADR 0003)

### 2. อัปเดตผ่าน manifest ที่ **ลงนามแล้ว** ไม่ใช่ HTTPS อย่างเดียว

```
GET https://api.example/app/v1/manifest.json
```

เสนอเปลี่ยน path จาก `/app-x/version.xd` เป็น `/app/v1/manifest.json` เพื่อให้ **รูปแบบไฟล์เองมี version**
จะได้เปลี่ยนโครงสร้างในอนาคตโดยแอปเก่าไม่พัง (นามสกุลไฟล์ไม่มีผลต่อความปลอดภัย)

```json
{
  "payload": {
    "package": "com.example.driver",
    "latest_version": "1.4.2",
    "latest_version_code": 142,
    "min_supported_version_code": 130,
    "apk_url": "https://api.example/app/v1/driver-1.4.2.apk",
    "apk_sha256": "9f2c…",
    "apk_size": 28374619,
    "signing_cert_sha256": "3a7b…",
    "mandatory": true,
    "release_notes_th": "…",
    "sequence": 47,
    "published_at": "2026-07-20T10:00:00Z",
    "expires_at": "2026-07-27T10:00:00Z"
  },
  "signature": "base64(ES256 over canonical JSON of payload)",
  "key_id": "release-2026-01"
}
```

**`payload` ต้องลงนามด้วย release signing key แยกต่างหาก (ES256 หรือ Ed25519) ที่ไม่ได้อยู่บนเซิร์ฟเวอร์**
ลงนามแบบออฟไลน์แล้วอัปโหลดเฉพาะไฟล์ที่ลงนามเสร็จแล้ว (ADR 0008 ตัดทางเลือก CI ออก)
public key ฝังอยู่ในแอป **พร้อม backup public key อย่างน้อย 1 ตัวตั้งแต่เวอร์ชันแรก**

### 3. สิ่งที่แอปต้องตรวจก่อนติดตั้ง — ครบทุกข้อ ขาดข้อใดข้อหนึ่งไม่ได้

1. ลายเซ็นของ `payload` ถูกต้องตาม public key ที่ฝังไว้
2. `expires_at` ยังไม่หมดอายุ — กัน **freeze attack**
3. `sequence` มากกว่าค่าที่เครื่องเคยเห็น — กัน **replay** manifest เก่าที่ลงนามถูกต้อง
4. `latest_version_code` > versionCode ที่ติดตั้งอยู่ — **ห้าม downgrade เด็ดขาด** (rollback attack)
5. `apk_sha256` ของไฟล์ที่ดาวน์โหลดมาตรงกับใน manifest
6. signing cert ของ APK ตรงกับ `signing_cert_sha256` และตรงกับของแอปตัวเอง
7. ข้อใดไม่ผ่าน → หยุด แจ้งผู้ใช้ และ **รายงานขึ้น server** ห้ามลองใหม่เงียบๆ

## ผลที่ตามมา

**ผลดี**
- ตรงตามความต้องการทางธุรกิจ ไม่ต้องเปิดเผยการมีอยู่ของแอป
- ควบคุมจังหวะการปล่อยเวอร์ชันได้เอง ไม่ต้องรอรีวิวจาก store
- **มีกลไก push update เองแล้ว ทำให้ certificate pinning กับ API เป็นไปได้** (เดิมปฏิเสธเพราะพังแล้วแก้ไม่ได้)
  โดย **pin เฉพาะ web app (API) ไม่ pin ช่องอัปเดต** เพราะช่องอัปเดตคือช่องทางกู้คืน
  → ควรแยก manifest/APK ไปอยู่คนละ hostname กับ API เพื่อให้ pin แยกกันได้ (§11.5)

**ผลเสีย — ความเสี่ยงที่รุนแรงที่สุดที่เพิ่มเข้ามา**

- **ช่องอัปเดตกลายเป็นเป้าหมายที่มีค่าที่สุดในระบบทั้งหมด**
  ใครควบคุม endpoint นี้ได้ = ส่งมัลแวร์ลงโทรศัพท์คนขับทุกเครื่องพร้อมกัน
  เสียหายกว่าทุกภัยคุกคามอื่นในเอกสารนี้รวมกัน — และรุนแรงกว่าสิ่งที่ L3 ที่เพิ่งตัดทิ้งไปเคยปิดได้เสียอีก
  **การลงนาม manifest จึงไม่ใช่ของเสริม แต่เป็นเงื่อนไขขั้นต่ำที่ขาดไม่ได้**
- **release signing key กลายเป็นความลับชั้นเดียวกับ `.jks`** — หลุดแล้วเซ็น manifest ปลอมได้
- ผู้ใช้ถูกฝึกให้ยอมรับการติดตั้ง APK นอก store → ตกเป็นเหยื่อ APK ปลอมที่อ้างว่าเป็นแอปบริษัทได้ง่ายขึ้น
  **นี่เป็นความเสี่ยงที่เกิดจากการตัดสินใจนี้โดยตรง** ควรมีการสื่อสารกับคนขับว่าแอปจริงมาจากช่องทางไหนเท่านั้น
- ต้องดูแล compatibility กับ Android รุ่นใหม่เอง (ข้อกำหนด targetSdk, ข้อจำกัดของแอป sideload ที่เข้มขึ้นทุกเวอร์ชัน)
- **MVP ทำ Android เท่านั้น** — iOS อัปเดตตัวเองแบบนี้ไม่ได้ ถ้าขยายไป iOS ในอนาคตต้องหาช่องทางอื่น (Enterprise Program / TestFlight)

## ทางเลือกที่พิจารณาแล้วไม่เลือก

| ทางเลือก | เหตุผลที่ไม่เลือก |
|---|---|
| Play Store แบบ internal testing / closed track | ได้ Play Integrity + อัปเดตอัตโนมัติ + Play Protect โดยแอปไม่ปรากฏต่อสาธารณะ — **แต่เจ้าของงานปฏิเสธการขึ้น store ทุกรูปแบบ** |
| MDM / EMM (จัดการอุปกรณ์จากส่วนกลาง) | เหมาะที่สุดถ้าเครื่องเป็นของบริษัท — แต่คนขับใช้เครื่องส่วนตัว จึงบังคับไม่ได้ |
| manifest ผ่าน HTTPS เฉยๆ ไม่ลงนาม | เซิร์ฟเวอร์ถูกเจาะ / CDN หลุด / CA ออกใบรับรองผิด = ส่งมัลแวร์ลงทุกเครื่อง **ยอมรับไม่ได้** |
| ให้ผู้ใช้ดาวน์โหลด APK เองจากเว็บทุกครั้ง | ผู้ใช้ไม่อัปเดต ทำให้เวอร์ชันที่มีช่องโหว่ค้างอยู่ในระบบนาน และแยกไม่ออกจากเว็บปลอม |
