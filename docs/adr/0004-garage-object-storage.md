## บริบท

กระบวนการรับสมัครเป็นกระดาษก่อน: คนขับยื่น **ใบสมัคร + สำเนาบัตรประชาชน + สำเนาใบขับขี่**
เจ้าหน้าที่ตรวจแล้วถ้าอนุมัติจึงบันทึกข้อมูลเข้าระบบพร้อม**อัปโหลดเอกสารทั้งหมด**

ไฟล์เหล่านี้คือข้อมูลส่วนบุคคลที่อ่อนไหวที่สุดในระบบ — สำเนาบัตรประชาชนใช้สวมรอยตัวตนได้โดยตรง
และมีมูลค่าในตลาดมืด สูงกว่าข้อมูลอื่นทุกอย่างที่ระบบนี้เก็บ

เจ้าของงานกำหนดให้ **แยกเก็บลง object storage อย่าง Garage**

## การตัดสินใจ

เก็บไฟล์ทั้งหมดใน **Garage** (object storage แบบ self-hosted ที่พูด S3 API)
ฐานข้อมูลเก็บเฉพาะ metadata ในตาราง `driver_documents` — `object_key`, `bucket`, `content_type`, `size_bytes`, `sha256`

### เงื่อนไขบังคับ

| กฎ | เหตุผล |
|---|---|
| **bucket ต้อง private ทั้งหมด** ห้ามเปิด public read | bucket ที่ตั้งค่าผิดคือสาเหตุข้อมูลรั่วที่พบบ่อยที่สุดในระบบแบบนี้ |
| **`object_key` ต้องสุ่ม** ห้ามมีชื่อคน เลขบัตร หรือเลขเรียงลำดับ | key ที่เดาได้ = ข้อมูลรั่วแม้ bucket จะ private และ key เองก็เป็นข้อมูลรั่วในตัว |
| ~~เข้าถึงผ่าน presigned URL อายุ ≤ 5 นาที~~ | **ยกเลิก — ดู ADR 0005** |
| **ทุกการเปิดดูเขียน `audit_logs` (`document.viewed`)** | PDPA ต้องตอบได้ว่าใครดูเอกสารของใครเมื่อไหร่ |
| ~~ห้าม proxy ไฟล์ผ่าน PHP~~ | **ยกเลิก — ดู ADR 0005** การถอดรหัสต้องเกิดฝั่ง server |
| **access key ที่แอปใช้ต้องจำกัดสิทธิ์เฉพาะ bucket ที่ใช้** ห้ามใช้ admin key ของ Garage | จำกัดความเสียหายเมื่อ key รั่ว |

### การรับไฟล์

- อนุญาตเฉพาะ `image/jpeg`, `image/png`, `application/pdf`
- **ตรวจจาก magic bytes ของไฟล์จริง ไม่ใช่จาก `Content-Type` header หรือนามสกุล**
- จำกัดขนาด 10 MB ต่อไฟล์
- รูปภาพ **re-encode ใหม่ทั้งหมด** เพื่อลบ EXIF (อาจมีพิกัด GPS ของที่ที่ถ่าย) และตัด payload ที่ฝังมากับไฟล์
- PDF อย่างน้อยตรวจว่าไม่มี JavaScript ฝังอยู่
- เก็บ `sha256` เพื่อตรวจภายหลังว่าไฟล์ไม่ถูกแก้

## ผลที่ตามมา

**ผลดี**
- ไฟล์ไม่หายเมื่อ container ถูกสร้างใหม่ — ต่างจากการเก็บบนดิสก์ของ container
- ฐานข้อมูลไม่บวมด้วย binary ทำให้ `pg_dump` ยังเร็วและ restore ยังทำได้ในเวลาที่ยอมรับได้
- ขยายที่เก็บได้แยกจากฐานข้อมูล
- Garage เป็น self-hosted ข้อมูลอ่อนไหวไม่ต้องออกนอกโครงสร้างพื้นฐานของเรา (ต่างจาก S3 ของ cloud เจ้าใหญ่) ซึ่งช่วยเรื่อง PDPA
- ใช้ S3 API มาตรฐาน → Laravel ใช้ filesystem driver `s3` เดิมได้ ไม่ต้องเขียน adapter เอง และย้ายไปที่เก็บอื่นในอนาคตได้

**ผลเสีย / ต้นทุน**
- **มี service ที่ต้องดูแลเพิ่มอีกตัว** — ต้อง monitor, backup, upgrade แยกจาก Postgres
- **backup ต้องครอบ Garage ด้วย** — ถ้า backup แค่ Postgres ข้อมูลจะไม่ครบ และจะรู้ตัวตอนที่กู้คืนแล้วเอกสารหายหมด
- **backup ของ Garage มีสำเนาบัตรประชาชนอยู่ข้างใน** → ต้องเข้ารหัสและคุมสิทธิ์เท่ากับระบบจริง
- Garage ต้องเปิด **path-style endpoint** — ไม่รองรับ virtual-host style แบบ AWS ต้องตั้ง config ให้ถูกไม่งั้นต่อไม่ติด
- ความสอดคล้องระหว่าง DB กับ storage ไม่ได้อยู่ใน transaction เดียวกัน → ถ้าอัปโหลดสำเร็จแต่ commit DB ล้ม จะเหลือ orphan object
  **ต้องมี job เก็บกวาด object ที่ไม่มีแถวใน `driver_documents` อ้างถึง**

> **ต้อง verify ตอน implement:** ความสามารถของ Garage เวอร์ชันที่จะ pin จริง — versioning, server-side encryption,
> lifecycle rule สำหรับ retention ความรู้ของผมถึงต้นปี 2026 อย่าเชื่อว่ามีฟีเจอร์เหล่านี้จนกว่าจะเช็คเอกสารของเวอร์ชันนั้น

## ทางเลือกที่พิจารณาแล้วไม่เลือก

| ทางเลือก | เหตุผลที่ไม่เลือก |
|---|---|
| เก็บเป็น `bytea` ใน PostgreSQL | DB บวมเร็ว, `pg_dump`/restore ช้าจนใช้งานจริงไม่ได้, เปลือง memory ตอนอ่าน |
| เก็บบนดิสก์ของ container (`storage/app`) | หายเมื่อสร้าง container ใหม่, backup ครอบไม่ถึง, ขยาย service เป็นหลายตัวไม่ได้ |
| S3 / cloud storage เจ้าใหญ่ | ข้อมูลอ่อนไหวออกนอกโครงสร้างพื้นฐาน มีประเด็น PDPA เรื่องการโอนข้อมูล และเจ้าของงานกำหนด Garage มาแล้ว |
| MinIO | ทางเลือกที่ใกล้เคียงกัน แต่เจ้าของงานระบุ Garage มาโดยตรง — ถ้าจะเปลี่ยนภายหลังทำได้เพราะทั้งคู่พูด S3 API เหมือนกัน |
