# Threat Model — Mobile & API Security Hardening

| | |
|---|---|
| ขอบเขต | Flutter app, API `/api/v1`, Staff Portal, ทะเบียนคนขับ, **ช่องแจกจ่าย/อัปเดตแอป** |
| อ้างอิง | `PRD.md`, `docs/architecture.md` |
| สถานะ | ฉบับร่าง — ยังไม่ได้ผ่านการทบทวนกับเจ้าของงาน |

> **ข้อสมมติพื้นฐาน**: อะไรก็ตามที่รันอยู่บนเครื่องผู้ใช้ ถือว่าอยู่ในมือ attacker ได้ทั้งหมด
> โค้ดแอป, ค่าคงที่ในแอป, ผลตรวจ root, ค่าที่แอปส่งมา — ปลอมได้หมด
> การป้องกันที่นับได้จริงต้องเกิดฝั่ง server หรืออยู่ในฮาร์ดแวร์ที่ export ไม่ได้

## 1. ทรัพย์สินที่ต้องปกป้อง

| # | ทรัพย์สิน | ผลถ้าหลุด |
|---|---|---|
| A1 | สิทธิ์เรียก API (และข้อมูลธุรกิจที่อยู่ข้างหลัง) | ผู้ไม่ได้รับอนุญาตเข้าถึงระบบ |
| A2 | Activation code / token | ลงทะเบียนอุปกรณ์เถื่อนได้ |
| A3 | Private key ของอุปกรณ์ | ปลอมเป็นอุปกรณ์ที่ลงทะเบียนแล้ว |
| A4 | PIN ของคนขับ | เข้าถึงแอปบนเครื่องที่ขโมยมา |
| A5 | บัญชีเจ้าหน้าที่ / Staff Portal | ออก code ได้ไม่จำกัด + รีเซ็ต PIN เครื่องใครก็ได้ = เจาะระบบทั้งระบบ |
| A6 | Release keystore (`.jks`) | เซ็นแอปปลอมที่ผ่าน L1 ได้ทุกอย่าง — **ความเสียหายสูงสุด** |
| A7 | Device UUID / metadata | ข้อมูลระบุตัวบุคคล เสี่ยงผิด PDPA |
| A8 | **ข้อมูลส่วนบุคคลของคนขับ** — ชื่อ, เลขบัตรประชาชน, เบอร์โทร, ใบขับขี่ | ผิด PDPA โดยตรง เสี่ยงถูกสวมตัวตน |
| A9 | **ช่องอัปเดตแอป (manifest + release signing key)** | **ควบคุมได้ = ส่งมัลแวร์ลงโทรศัพท์คนขับทุกเครื่องพร้อมกัน** — ทรัพย์สินที่ควบคุมแล้วเสียหายกว้างที่สุดในระบบ |
| A10 | **สำเนาบัตรประชาชน + สำเนาใบขับขี่ + ใบสมัคร ใน Garage** | **ทรัพย์สินที่อ่อนไหวที่สุดในระบบ** — ใช้สวมรอยตัวตนได้ทันที มีมูลค่าในตลาดมืด และกู้คืนความเสียหายไม่ได้ (เปลี่ยนเลขบัตรประชาชนไม่ได้) |

## 2. ผู้โจมตีที่พิจารณา

| # | ใคร | ความสามารถ |
|---|---|---|
| T1 | คนนอก มีแค่ APK ที่เผยแพร่แล้ว | decompile, ดึงค่าคงที่, เขียน client เอง |
| T2 | ผู้ใช้ที่ถูกต้อง แต่ root เครื่องตัวเอง | Frida, Magisk Hide, hook ทุกฟังก์ชันในแอป |
| T3 | คนที่ขโมยเครื่องมาได้ | เข้าถึงเครื่องจริง อาจปลดล็อกได้หรือไม่ก็ได้ |
| T4 | ผู้ดักกลางเครือข่าย | ดัก/แก้ traffic บน Wi-Fi สาธารณะ |
| T5 | เจ้าหน้าที่ที่มีเจตนาไม่ดี | ออก activation code ให้ตัวเอง, รีเซ็ต PIN เครื่องคนอื่น, ดูข้อมูลส่วนบุคคลของคนขับ |
| T6 | ผู้เข้าถึง repo หรือเครื่องที่ build release | ขโมย `.jks`, ฝัง backdoor ใน build |
| T7 | คนนอกที่แกล้งสมัครเป็นคนขับ | ใช้เอกสารปลอมหรือของคนอื่นลงทะเบียนเข้าระบบ |
| T8 | **ผู้ที่ควบคุมช่องอัปเดตแอปได้** | เจาะเซิร์ฟเวอร์/CDN, ยึดบัญชี, หรือเป็นคนใน → ส่ง APK ปลอมลงทุกเครื่อง |

**ไม่พิจารณาในรอบนี้:** การโจมตีระดับรัฐ, ฮาร์ดแวร์ decap chip, การโจมตี Google/Apple root of trust

## 3. สถานการณ์การโจมตี

### S1 — เขียน client เองแล้วยิง API ตรง (T1 → A1)
คู่แข่งหรือ bot ดึง `X-App-Signature` จาก APK แล้วเขียนสคริปต์ยิง API

- **PRD ให้อะไร:** L1 อย่างเดียว — **กันไม่ได้** fingerprint เป็นค่าสาธารณะ ดูได้ด้วย `apksigner verify --print-certs`
- **มาตรการ:** L2 device signature — ต้องมี private key ที่อยู่ใน hardware keystore ของเครื่องที่ลงทะเบียนแล้วเท่านั้น attacker ที่ไม่มีอุปกรณ์ที่ enroll แล้วจะเซ็นไม่ได้
- **ความเสี่ยงที่เหลือ:** ถ้า attacker มีอุปกรณ์ที่ enroll ถูกต้อง 1 เครื่อง ก็ใช้เครื่องนั้นเป็นทางผ่านได้ → **L3 ถูกตัดทิ้งแล้ว (ADR 0003)** เหลือแค่ rate limit ต่ออุปกรณ์ + ตรวจจับพฤติกรรมผิดปกติฝั่ง server

### S2 — Replay request ที่ดักมาได้ (T4 → A1)
- **มาตรการ:** `X-Nonce` เก็บใน Valkey TTL 5 นาที (ซ้ำ = ปฏิเสธ) + `X-Timestamp` ยอมรับ skew ±60 วินาที + TLS
- **ความเสี่ยงที่เหลือ:** ถ้า Valkey หายทั้งชุด nonce เก่าจะกลับมาใช้ได้ชั่วคราว → Valkey ต้องมี persistence และรวมอยู่ในแผน monitoring

### S3 — โคลนอุปกรณ์ / ยกข้อมูลไปเครื่องอื่น (T2 → A3)
- **PRD ให้อะไร:** ผูกด้วย "Hardware UUID" — **กันไม่ได้** ค่านี้อ่านและปลอมได้บนเครื่อง root
- **มาตรการ:** private key สร้างใน Android Keystore (StrongBox ถ้ามี) โดยตั้ง `export = false` → คัดลอกออกจากเครื่องไม่ได้แม้ root แล้ว
- **ความเสี่ยงที่เหลือ:** เครื่อง root ยังใช้ key ผ่าน keystore API ได้ (ใช้ได้ แต่ก๊อปไม่ได้) → **Key Attestation ปฏิเสธเครื่องที่ bootloader ปลดล็อกตั้งแต่ตอน enroll** (§4.2) + ผูก key เข้ากับ biometric/screen-lock

### S4 — Brute-force PIN (T3 → A4)
PIN 6 หลัก = 10⁶ ความเป็นไปได้ ถ้ายิงได้ 10 ครั้ง/วินาที เดาหมดในเวลาไม่ถึงวัน

- **มาตรการ:** ตรวจ PIN ที่ server เท่านั้น + lockout (ผิด 5 ครั้ง ล็อก 15 นาที, สะสม 10 ครั้ง → `blocked` + แจ้ง Admin) + ปฏิเสธ PIN ที่อ่อน (`111111`, `123456`, top-100) + rate limit ชั้นนอก
- **สำคัญ:** ห้ามให้แอปเทียบ PIN เองในเครื่อง — attacker ที่ถือเครื่องจะยิงแบบ offline ได้ไม่จำกัด
- **ความเสี่ยงที่เหลือ:** ยอมรับว่าเดาถูกโดยบังเอิญได้ ~0.001% ต่อ 10 ครั้ง → ยอมรับได้เพราะยังต้องผ่าน L2 ด้วย

### S5 — Bypass root detection (T2 → A1) — 🔴 **เปิดถาวร ไม่มีทางปิด**
Magisk Hide / Zygisk / Frida ซ่อน root จากผลตรวจฝั่ง client ได้

- **PRD ให้อะไร:** ตรวจฝั่ง client แล้วปิดแอป — **เลี่ยงได้** และแย่กว่านั้นคือ**เราไม่มีทางรู้ว่าถูกเลี่ยง**เพราะผลไม่เคยส่งขึ้น server
- **มาตรการ:** บังคับส่ง `IntegritySignals` ขึ้น server ทุกครั้งที่เปิดแอป → server คิด `risk_score` และเป็นคนตัดสิน `allow`/`warn`/`block` → เก็บใน `integrity_reports` เพื่อดูแนวโน้ม
- **✅ มาตรการที่ตรวจได้จริง — Android Key Attestation (L2.5)**
  ผลตรวจฝั่งแอปเชื่อไม่ได้ แต่ **ฮาร์ดแวร์ตอบแทนแอปได้** — TEE/StrongBox เซ็น certificate chain
  ที่สืบสาวถึง root ของ Google และมี `verifiedBootState` / `deviceLocked` อยู่ข้างใน
  **เครื่อง root ส่วนใหญ่ต้องปลดล็อก bootloader ก่อน จึงถูกจับได้ตรงนี้** และ Frida hook ไม่ได้
  เพราะการตรวจเกิดฝั่ง server บนใบรับรองที่แอปแก้ไม่ได้ (§4.2)
  **ไม่ต้องใช้ Play Store** ต่างจาก Play Integrity
- **ความเสี่ยงที่เหลือ: กลาง (ลดลงจาก "สูง" หลังเพิ่ม L2.5)**
  ยังไม่ปิด: เครื่องที่ **bootloader ล็อกอยู่** แต่ถูก exploit ระดับ runtime ภายหลัง
  หรือ attestation key ของผู้ผลิตที่รั่วออกมาแล้วถูกนำไปปลอม (Google ทยอยเพิกถอน — ควรตรวจ revocation ด้วย)
  ส่วนนี้คือสิ่งที่ Play Integrity ปิดได้และเราไม่มี (ADR 0003) → เหลือการ **ตรวจจับ** ฝั่ง server (§11.4)

### S6 — ขโมย/เดา Activation code (T1 → A2)
- **มาตรการ:** อายุ 15 นาที, ใช้ได้ครั้งเดียว, DB เก็บแค่ hash, JWT ลงนาม ES256 (ห้าม HS256 — shared secret จะต้องฝังในแอป), rate limit ต่อ code และต่อ IP, Admin เพิกถอนได้
- **ความเสี่ยงที่เหลือ:** ถ้า QR ถูกถ่ายรูปไว้ในช่วง 15 นาที ก็ใช้ได้ → ควรให้ Admin เห็นทันทีว่า code ถูกใช้จากเครื่องอะไร

### S7 — ยึดบัญชีเจ้าหน้าที่ / Staff Portal (T1/T5 → A5, A8)
ถ้าได้บัญชีเจ้าหน้าที่ = ออก code ได้ไม่จำกัด + **รีเซ็ต PIN เครื่องใครก็ได้** + ดูข้อมูลส่วนบุคคลของคนขับทั้งฐาน

- **มาตรการ:** บังคับ TOTP 2FA, rate limit หน้า login, session cookie `HttpOnly`/`Secure`/`SameSite=Strict`, CSRF token, จำกัด IP ถ้าทำได้, ทุกการกระทำเขียน `audit_logs` แบบ append-only, แจ้งเตือนเมื่อออก code / รีเซ็ต PIN / เปิดดูข้อมูลส่วนบุคคล ถี่ผิดปกติ
- **ความเสี่ยงที่เหลือ:** เจ้าหน้าที่ที่มีเจตนาไม่ดี (T5) กันไม่ได้ด้วยเทคนิค — กันได้แค่ทำให้ตรวจย้อนหลังได้ → ควรมี 4-eyes สำหรับการออก code จำนวนมาก (นอกขอบเขต MVP)

### S12 — เจ้าหน้าที่ใช้ช่องรีเซ็ต PIN เพื่อยึดเครื่องคนขับ (T5 → A1, A4) — *ช่องทางใหม่*

เจ้าของงานยืนยันว่า **เจ้าหน้าที่รีเซ็ต PIN ให้คนขับได้** ซึ่งจำเป็นในทางปฏิบัติ
แต่ในเชิงความปลอดภัยนี่คือ **ทางลัดที่ข้าม PIN ได้ทั้งหมด** และเป็นช่องที่ไม่มีอยู่ก่อนหน้านี้

สถานการณ์: เจ้าหน้าที่รีเซ็ต PIN เครื่องของคนขับที่ไม่ได้ร้องขอ แล้วตั้ง PIN ใหม่เองบนเครื่องที่ยึดมา

- **มาตรการ:** บังคับ 2FA กับบัญชีเจ้าหน้าที่, เขียน `audit_logs` (`pin.reset`) ทุกครั้งพร้อมระบุตัวเจ้าหน้าที่, rate limit 20 ครั้ง/ชั่วโมง และแจ้งเตือนเมื่อเกิน, แจ้งคนขับทุกครั้งที่มีการรีเซ็ต PIN บนเครื่องของตน
- **สำคัญ:** การรีเซ็ต PIN **ไม่ได้ให้เครื่องใหม่** — ยังต้องใช้ device keypair ในเครื่องเดิม ดังนั้นเจ้าหน้าที่ต้องมีเครื่องจริงอยู่ในมือด้วยถึงจะใช้ช่องนี้ได้ ซึ่งจำกัดความเสียหายลงมาก
- **ความเสี่ยงที่เหลือ:** เจ้าหน้าที่ที่ถือเครื่องคนขับอยู่ (เช่น ตอนรับเรื่องซ่อม) ทำได้ → ต้องคุมด้วยกระบวนการ ไม่ใช่เทคนิค

### S13 — สมัครด้วยเอกสารปลอมหรือของคนอื่น (T7 → A1, A8)

- **มาตรการ:** **ไม่มี self-registration เลย** — คนขับยื่นเอกสารกระดาษ เจ้าหน้าที่ตรวจ ถ้าอนุมัติจึงเป็นคนกรอกเข้าระบบเอง
  ประตูเข้าระบบเดียวคือเจ้าหน้าที่ ไม่มี API ที่คนนอกใช้สร้างตัวตนได้ + กันสมัครซ้ำด้วย `national_id_hmac` unique
- **ความเสี่ยงที่เหลือ:** การตรวจเอกสารด้วยตาเจ้าหน้าที่จับเอกสารปลอมคุณภาพสูงไม่ได้
  ถ้าต้องการมากกว่านี้ต้องต่อ e-KYC หรือตรวจกับฐานทะเบียนราษฎร ซึ่งอยู่นอกขอบเขต MVP
- **หมายเหตุ:** โครงสร้างนี้ดีกว่าแบบ self-registration อย่างมีนัยสำคัญ — ความเสี่ยงย้ายจาก "ใครก็สมัครได้" มาเป็น "คุณภาพการตรวจเอกสารของเจ้าหน้าที่" ซึ่งควบคุมด้วยกระบวนการและฝึกอบรมได้

### S14 — เอกสารใน Garage รั่ว (T1/T5/T6 → A10) — **ความเสี่ยงสูงสุดด้าน PDPA**

Garage เก็บสำเนาบัตรประชาชนของคนขับทุกคน — ถ้า bucket ตั้งค่าผิดหรือ key รั่ว คือเหตุข้อมูลรั่วเต็มรูปแบบ
และ **กู้คืนความเสียหายไม่ได้** เพราะคนขับเปลี่ยนเลขบัตรประชาชนไม่ได้

- **มาตรการ:**
  - bucket **private ทั้งหมด** ห้ามเปิด public read เด็ดขาด — ต้องมีการตรวจ config ข้อนี้เป็นประจำ
  - `object_key` **สุ่ม** ห้ามมีชื่อคน เลขบัตร หรือเลขเรียงลำดับ (key ที่เดาได้ = รั่วแม้ bucket private)
  - **ไฟล์เข้ารหัสก่อนอัปโหลดเสมอ** (envelope encryption, ADR 0005) → สิ่งที่อยู่ใน Garage เป็น ciphertext ล้วน
  - เข้าถึงผ่าน endpoint ที่ต้องมี **สิทธิ์ + step-up PIN** เท่านั้น (ไม่ใช้ presigned URL แล้ว — ดู ADR 0005)
  - access key ที่แอปใช้จำกัดสิทธิ์เฉพาะ bucket ที่จำเป็น **ห้ามใช้ admin key ของ Garage**
  - ทุกการเปิดดูเขียน `audit_logs` (`document.viewed`) + rate limit 60 ครั้ง/ชั่วโมงต่อเจ้าหน้าที่ พร้อมแจ้งเตือนเมื่อเกิน (สัญญาณของการดูดข้อมูล)
  - รูปภาพ re-encode ใหม่เพื่อลบ EXIF (พิกัด GPS) และตัด payload ที่ฝังมากับไฟล์; ตรวจชนิดไฟล์จาก magic bytes ไม่ใช่จาก header
  - **backup ของ Garage ต้องเข้ารหัสและคุมสิทธิ์เท่ากับระบบจริง** — backup คือสำเนาเต็มของทรัพย์สินชิ้นนี้
- **ความเสี่ยงที่เหลือ:**
  - เจ้าหน้าที่ที่มีสิทธิ์ยังดาวน์โหลดเอกสารทีละไฟล์ได้ กันด้วยเทคนิคไม่ได้ — ได้แค่ตรวจจับผ่าน audit + rate limit
  - **retention ยังไม่ได้ตกลง** ทุกวันที่เก็บเอกสารไว้เกินความจำเป็นคือความเสี่ยงที่สะสมโดยไม่ได้ประโยชน์ → ต้องได้ข้อสรุปก่อนขึ้น production

### S8 — `.jks` หลุด (T6 → A6) — **ความเสียหายสูงสุด**
ใครมี keystore ก็เซ็นแอปปลอมที่ผ่าน L1 ได้ทุกอย่าง และกู้คืนไม่ได้ (ต้องเปลี่ยน key ทั้งฐานผู้ใช้)

- **มาตรการ:** `.jks` อยู่บน **เครื่อง release เฉพาะ** เครื่องเดียว (ADR 0008) — ดิสก์เข้ารหัสทั้งลูก,
  ไฟล์ไม่ออกจากเครื่อง, password เก็บแยกใน password manager, ระบุผู้ถือเป็นชื่อคน,
  ไม่ใช้เครื่องนั้นทำงานทั่วไป · ห้ามเข้า repo และห้ามเข้า image layer (ADR 0002),
  `.gitignore` ครอบ `*.jks` / `*.keystore`, gitleaks ใน `.githooks/pre-commit` + `make secrets-scan`,
  branch protection บน `main`
- **🔴 ความเสี่ยงที่เหลือ — keystore *หาย* เสียหายพอกับ keystore *หลุด*:** เครื่องเดียวแปลว่าเครื่องพัง
  ถูกขโมย หรือดิสก์เสีย = **เซ็น APK ตัวใหม่ไม่ได้อีกเลย** Android ไม่ให้ติดตั้งทับแอปที่เซ็นด้วย key คนละดอก
  → ต้องให้คนขับทุกคนถอนแล้วติดตั้งใหม่ ซึ่งเป็นงานภาคสนามที่แพงมาก
  **มาตรการบังคับ:** backup ที่เข้ารหัส เก็บอย่างน้อย 2 ที่ที่ไม่พังพร้อมกัน (หนึ่งที่อยู่นอกออฟฟิศ)
  passphrase ไม่เก็บไว้ที่เดียวกับไฟล์ และ **ต้องทดสอบกู้คืนจริงก่อน release แรก**
- **🔴 ความเสี่ยงที่เหลือ — กุญแจครบชุดในเครื่องเดียว:** ถ้าเครื่อง release ถือทั้ง `.jks` และ
  `MANIFEST_SIGNING_KEY` คนที่ยึดเครื่องได้จะเซ็น APK ปลอม **และ** เซ็น manifest สั่งติดตั้งลงทุกเครื่อง
  ได้ในคราวเดียว = S8 รวมกับ T8 → ให้แยกที่เก็บกุญแจสองดอกนี้ถ้าทำได้ (ADR 0008)
- **ความเสี่ยงที่เหลือ:** ไม่มี CI แปลว่า **ไม่มีอะไรตรวจ build ให้** — APK ที่ปล่อยเป็นผลจากเครื่องของคนคนหนึ่ง
  ทางชดเชย: บันทึก `apk_sha256` ของทุก release และ pin เวอร์ชัน Flutter SDK ให้ตรงกันทุกเครื่อง

### S9 — เครื่องหาย (T3 → A1, A4)
- **มาตรการ:** คนขับแจ้งเจ้าหน้าที่ → เจ้าหน้าที่กด "ลบอุปกรณ์" (`revoke`, reason `lost`) → ทุก session ถูกยกเลิก → เครื่องได้ `401 E_DEVICE_REVOKED` แล้วล้างข้อมูลทิ้ง; access token อายุสั้น (15 นาที) จำกัดช่วงเวลาที่ยังใช้ได้
- **ความเสี่ยงที่เหลือ:** ช่วงเวลาระหว่างเครื่องหายจริงกับตอนที่เจ้าหน้าที่กด revoke — ยิ่งแจ้งช้ายิ่งเสี่ยง
  → **ยังไม่มีคำตอบว่านอกเวลาทำการทำยังไง** ถ้าเครื่องหายคืนวันศุกร์แล้วเจ้าหน้าที่มาวันจันทร์ = เปิดช่อง 3 วัน
  → ควรพิจารณาช่องทางแจ้งด่วน (สายด่วน / ปุ่มแจ้งในแอปจากเครื่องอื่น) หรือลด TTL ของ refresh token

### S10 — MITM / ปลอม certificate (T4 → A1, A2)
- **มาตรการ:** TLS 1.2 ขึ้นไป, HSTS, ไม่มี fallback เป็น HTTP; L2 device signature ทำให้ต่อให้ถอด TLS ได้ก็ยังปลอม request ไม่ได้
- **ตัดสินใจ (แก้จากรุ่นก่อน):** ✅ **ทำ certificate pinning กับ API (web app)** — SPKI pin + backup pin
  **ไม่ pin ช่องอัปเดต manifest/APK** เพราะเป็นช่องทางกู้คืน ถ้า pin ทั้งคู่แล้วพัง = แอปทั้งฐานกลายเป็นอิฐที่แก้ไม่ได้
  ความปลอดภัยของช่องอัปเดตมาจาก**ลายเซ็นบน manifest** ไม่ใช่ TLS ซึ่งแข็งแรงกว่า pinning อยู่แล้ว
  **ไม่เกี่ยวกับ Garage** — แอปไม่เคยต่อ Garage โดยตรง (§11.5)
- **ความเสี่ยงที่เหลือ:** ถ้าลืมต่ออายุ pin หรือไม่มี backup pin → แอปใช้ไม่ได้ทั้งฐาน
  ต้องมี runbook การต่ออายุ cert ที่ซ้อมแล้ว + pin set มีวันหมดอายุที่ fallback ไป system trust store ได้

### S11 — ข้อมูลส่วนบุคคลรั่ว (T1/T5 → A7, A8) — PDPA

ตอนนี้ระบบเก็บ **ข้อมูลส่วนบุคคลของคนขับเต็มรูปแบบ** (ชื่อ, เลขบัตรประชาชน, เบอร์โทร, ใบขับขี่, อาจมีรูปเอกสาร)
ซึ่งยกระดับความเสี่ยงจากเดิมที่มีแค่ device UUID อย่างมีนัยสำคัญ

- **มาตรการ:**
  - `national_id` **เข้ารหัสตอนเก็บ** + `national_id_hmac` แยกไว้ค้นหา/กันซ้ำ — **ห้าม plaintext**
  - `device_uuid` เก็บเป็น HMAC เท่านั้น, `pin` เป็น Argon2id, token เก็บแค่ hash
  - รูปบัตรประชาชน/ใบขับขี่เก็บนอกฐานข้อมูล มี access control **ห้ามอยู่ใน `public/`** และ path ต้องเดาไม่ได้
  - ห้าม log ค่าดิบทุกชนิดรวมถึงเลขบัตรประชาชน (บังคับด้วย redaction ใน logging config ไม่ใช่พึ่งวินัยคนเขียน)
  - API คืนข้อมูลคนขับแบบ **mask เป็นค่าเริ่มต้น** แสดงเต็มเฉพาะเมื่อมีสิทธิ์ และเขียน `audit_logs` (`driver.pii_viewed`) ทุกครั้ง
  - ห้ามใช้ข้อมูลจริงของคนขับใน seeder / fixture / test
- **ค้างอยู่:** ระยะเวลาเก็บข้อมูล (audit log, ข้อมูลคนขับ, รูปเอกสาร) ยังไม่ได้ตกลง — **ต้องคุยกับฝ่ายกฎหมายก่อนขึ้น production** และต้องมีขั้นตอนรองรับสิทธิ์ขอลบข้อมูลของเจ้าของข้อมูล

### S18 — ตั้ง `APP_ROLE` ผิด / secret รั่วข้ามฝั่ง (T6 → A9, A10) — *ช่องทางใหม่จากการแยก container*

การแยก `api` กับ `portal` (ADR 0007) ลดความเสี่ยงลงมาก แต่สร้างความผิดพลาดแบบใหม่ที่เกิดง่ายเวลา deploy

ถ้าตั้ง `APP_ROLE=portal` ให้ container ที่เปิดสู่อินเทอร์เน็ต หรือเผลอ mount `DOCUMENT_KEK` ให้ `api`
= **การแยกทั้งหมดไร้ผลทันทีโดยไม่มีอะไรฟ้อง** ระบบยังทำงานปกติทุกอย่าง

- **มาตรการ:**
  - **test ที่ต้องรันเอง** (`make test`, `make verify-isolation`): image ที่รันด้วย `APP_ROLE=api` ต้องตอบ `404` ที่ `/staff` และต้องไม่มี KEK ใน environment
  - `api` ไม่อยู่บน `garage-net` → ต่อ Garage ไม่ได้แม้ config จะผิด (**การป้องกันชั้นที่สอง ไม่พึ่ง config อย่างเดียว**)
  - ตรวจ compose ด้วย `make verify-isolation` ว่าไม่มี secret ต้องห้ามผูกกับ service `api`
  - Postgres และ Garage **ห้าม publish port ออกนอก host**
- **ความเสี่ยงที่เหลือ:** ความผิดพลาดตอน deploy ด้วยมือบนเครื่องจริง — ไม่มี CI ที่จะ deploy ให้ (ADR 0008)
  จึงต้องรัน `make verify-isolation` **หลัง recreate container ทุกครั้ง** ซึ่งเป็นขั้นตอนที่คนลืมได้

### S16 — ยึดช่องอัปเดตแอป (T8 → A9 → ทุกอย่าง) — 🔴 **ความเสี่ยงที่รุนแรงที่สุดในระบบ**

แอปไม่ขึ้น store จึงต้องอัปเดตตัวเองโดยเช็ค manifest จากเว็บของระบบทุกครั้งที่เปิด (§11.3, ADR 0006)
กลไกนี้ **สั่งให้โทรศัพท์คนขับทุกเครื่องดาวน์โหลดและติดตั้งไฟล์ได้**

ใครควบคุม endpoint นี้ได้ = ส่งมัลแวร์ลงทุกเครื่องพร้อมกัน อ่านทุกอย่างในเครื่อง รวมถึงข้ามทุกมาตรการในเอกสารนี้
**เสียหายกว่าทุกภัยคุกคามอื่นรวมกัน และรุนแรงกว่าสิ่งที่ L3 ที่เพิ่งตัดทิ้งไปเคยปิดได้เสียอีก**

เส้นทางโจมตี: เจาะเซิร์ฟเวอร์ · ยึดบัญชี CDN · CA ออกใบรับรองผิดพลาดหรือถูกบังคับ · คนในที่เข้าถึงเครื่องได้
**HTTPS ป้องกันได้แค่เส้นทางเดียวจากทั้งหมดนี้**

- **มาตรการที่ขาดไม่ได้ — ไม่ใช่ของเสริม:**
  - `payload` ต้อง **ลงนามด้วย release key แยกที่ไม่ได้อยู่บนเซิร์ฟเวอร์** (ลงนามออฟไลน์ด้วย `scripts/sign-manifest.sh`) public key ฝังในแอป
  - ฝัง **backup public key** ตั้งแต่เวอร์ชันแรก ไม่งั้นกุญแจหลักหลุดแล้วจะอัปเดตแก้ไม่ได้เลย
  - `expires_at` กัน freeze attack · `sequence` กัน replay · ห้าม downgrade กัน rollback
  - ตรวจ `apk_sha256` และ signing cert ของ APK ก่อนติดตั้ง
  - **ห้าม pin certificate ของ host ที่เสิร์ฟ manifest/APK** — เป็นช่องทางกู้คืน ถ้า pin พังจะอัปเดตแก้ไม่ได้เลย
  - แยก manifest/APK ไปคนละ hostname กับ API เพื่อให้ pin เฉพาะ API ได้ (§11.5)
- **ความเสี่ยงที่เหลือ:**
  - **release signing key กลายเป็นความลับชั้นเดียวกับ `.jks`** — หลุดแล้วเซ็น manifest ปลอมได้ ต้องเก็บและหมุนอย่างเข้มงวด
  - ผู้ใช้ถูกฝึกให้ยอมรับติดตั้ง APK นอก store → ตกเป็นเหยื่อ **APK ปลอมที่อ้างว่าเป็นแอปบริษัท** ได้ง่ายขึ้น
    กันด้วยเทคนิคไม่ได้ ต้องสื่อสารกับคนขับว่าแอปจริงมาจากช่องทางไหนเท่านั้น
  - ไม่มี Play Protect คอยสแกนมัลแวร์ให้อีกชั้น

### S17 — "ไม่มีใครรู้ว่ามีแอปนี้" ถูกใช้แทนมาตรการความปลอดภัย (T1 → ทุกอย่าง)

เหตุผลของการไม่ขึ้น store คือไม่ต้องการให้คนรู้ว่ามีแอปนี้อยู่ — เป็นความต้องการทางธุรกิจที่ชอบธรรม
**แต่ห้ามนับเป็นมาตรการความปลอดภัย**

APK จะอยู่ในมือคนขับหลายพันเครื่อง ไฟล์รั่วออกไปแน่นอน เป็นเรื่องของเวลา
ใครได้ไปก็ decompile เห็น endpoint และค่าคงที่ทั้งหมด

- **มาตรการ:** ออกแบบทุกอย่างโดย **ไม่พึ่งพาความลับของตัวแอปเลย** — ให้ถือว่าวันที่ APK อยู่บนอินเทอร์เน็ตสาธารณะมาถึงแล้ว
- **ความเสี่ยงที่เหลือ:** เชิงองค์กร — ถ้าทีมหรือลูกค้าเข้าใจผิดว่า "ไม่มีใครรู้" คือการป้องกัน จะละเลยมาตรการอื่น
  ต้องระบุให้ชัดในเอกสารส่งมอบ

1. **ช่องอัปเดตแอป (S16)** — เกิดจากการตัดสินใจไม่ขึ้น store
   ยึดได้ = ส่งมัลแวร์ลงทุกเครื่องพร้อมกัน ข้ามทุกมาตรการในเอกสารนี้
   **การลงนาม manifest ด้วย key ที่ไม่ได้อยู่บนเซิร์ฟเวอร์ คือเงื่อนไขขั้นต่ำที่ขาดไม่ได้**
2. **กองสำเนาบัตรประชาชนใน Garage (S14)** — รั่วแล้วกู้คืนไม่ได้เพราะเปลี่ยนเลขบัตรไม่ได้
   ป้องกันได้ด้วยเรื่องพื้นๆ: เข้ารหัสก่อนเก็บ, ตั้ง bucket ให้ถูก, key สุ่ม, ไม่เก็บนานเกินจำเป็น

ทั้งสองข้อควรได้รับความสำคัญ **ไม่น้อยกว่า** เรื่อง anti-tampering ที่ `PRD.md` เน้น

**เรื่องการตรวจ device:** แอปตรวจ root ได้ แต่**ผลจากแอปเชื่อไม่ได้** เพราะโค้ดรันบนเครื่องของ attacker
ตัวที่เชื่อได้คือ **Android Key Attestation** ซึ่งให้ฮาร์ดแวร์เป็นคนตอบแทนแอป ตรวจฝั่ง server
และ **ไม่ต้องใช้ Play Store** — ปิดเคสเครื่อง root ส่วนใหญ่ได้จริง (§4.2)

**บันทึกไว้ให้ชัด:** การไม่ขึ้น store แลกความสามารถ (L3) กับความเสี่ยงใหม่ (S16 ช่องอัปเดต)
Key Attestation ชดเชยฝั่ง L3 ได้พอสมควร แต่ **S16 เป็นความเสี่ยงที่เพิ่มเข้ามาสุทธิและต้องคุมด้วยการลงนาม manifest ให้ถูกต้อง**
